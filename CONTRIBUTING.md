# Contributor Guide

Thank you for your interest in contributing to DLSite List. This project is open-source under the [MIT License](LICENSE) and welcomes bug reports, feature requests, documentation improvements, and code contributions.

## Documentation

These resources are a good place to start:

- [README](README.md) — project overview and quick start.
- [Configuration](docs/CONFIGURATION.md) — installation, environments, and application settings.
- [Architecture](docs/ARCHITECTURE.md) — how the application and its features work.
- [Testing](docs/TESTING.md) — test setup, commands, and existing coverage.

You don't need to read everything to report a bug or suggest an idea. Check the relevant documentation if you're unsure how something is meant to work.

## How to report a bug

Search the [issue tracker](https://github.com/Arednel/DLSite-List/issues) before opening a new issue. When reporting a bug, please include:

- Your operating system and installation method (manual or Docker).
- The DLSite List version you're using.
- What happened and what you expected to happen.
- Steps to reproduce the problem, if possible.
- Relevant error messages, logs, or screenshots, if available.

Provide as much relevant information as you can, even if you're unsure what causes the problem.

## How to request a feature

You can suggest features through [Discussions](https://github.com/Arednel/DLSite-List/discussions) or open an [issue](https://github.com/Arednel/DLSite-List/issues) for a more concrete request. Please check for similar discussions or issues first.

Describe what you'd like to add or improve, why it would be useful, and how you expect it to work.

Examples or mockups are welcome, but you don't need to propose code. The important part is understanding and clearly explaining what you're requesting.

## How to set up development

Follow the [Configuration guide](docs/CONFIGURATION.md) to set up the project.

For changes to unfamiliar features, read the relevant parts of the [Architecture guide](docs/ARCHITECTURE.md) and existing code before starting. For larger changes, consider discussing the approach in an issue or Discussion first.

## How to test your changes

See the [Testing guide](docs/TESTING.md) for the available commands. Please run relevant tests before submitting a pull request.

## How to submit changes

Changes can be submitted through [pull requests](https://github.com/Arednel/DLSite-List/pulls) for review and discussion. Explain what changed, why it was needed, and how you tested it. Link any related issues or discussions and be open to feedback and revisions.

If your changes are still in progress, you can open a draft pull request to discuss your approach or request feedback.

To keep pull requests easy to review:

- Keep each pull request focused on a specific change. Avoid unrelated refactoring or formatting changes.
- Review your changes before submitting and make sure they work as intended.
- Update the relevant documentation when necessary.

## AI-assisted contributions

AI assistance is welcome for bug reports, feature requests, documentation, and code contributions. Please review and understand any AI-assisted content before submitting it:

- **Bug reports:** Verify the problem yourself. You don't need to know its technical cause.
- **Feature requests:** Understand the functionality you're asking for and the behavior you expect.
- **Pull requests:** Review the code, understand what it changes and how it works, and be able to explain or revise it during review.

Don't submit unreviewed AI-generated content or present untested changes as tested.
